# CAM Muse Hybrid Gateway V1 — pilot integration core

Status: **OFFLINE / MOCK PILOT**, not a live worker or renderer cutover.
Baseline CAM release: 089bd59a6611703703a2b1fe394f6343ca2f813f (Bridge 1.4.23).
Reviewed LynByte reference: 6050d45d3c99d89664cfff0a0a5c830aa9569f36.
This is independent integration code, not a full fork of LynByte.

## Run offline acceptance

Python 3.10+ (tested on Python 3.12), standard library only.
Local FFmpeg and FFprobe are used in the synthetic technical-video tests.
From this directory:

    python -m unittest discover -s . -p "test_*.py" -v

No tests make a production claim, call a provider, launch a browser, use
account credentials, emit worker telemetry, or write to Drive. The local
MP4 fixture validates the technical media checks, not visual product QA.

## What is implemented

- core.py: immutable logical render identity (tenant/listing/original SHA/
  C1717/aspect/story version/take/authorized generation revision); single-owner
  OS lock; atomic bounded JSON journal; request fingerprint; exact hero bytes;
  conservative submit/status/reconcile state machine; CAM long-poll dispatcher.
- media.py: bounded local media spool and FFprobe checks matching the CAM
  1.4.23 codec/size/ratio/duration checks. Pass exact claimed duration bounds.
  Never pad or transcode. Stage only media verified to belong to the exact
  backend task. Cleanup only after the CAM receipt has been verified.
- test_core.py, test_media.py: mock transport, restart/race/timeout/partial/
  cooldown/receipt cases and local H.264 fixture.

This does not add a business queue, new database service, VPS or AI API.
The existing CAM database, private Drive objects and R2 cache remain canonical.
The technical journal/spool is local to the owning worker, not shared between
accounts. It keeps ambiguous tasks rather than silently retrying or evicting
them. A capacity or corrupt-journal warning requires reconciliation, not deletion.

## Integration boundary (required before any live use)

1. Register a dedicated authorized workstation workspace and verify its
   Python 3.10+, FFmpeg/FFprobe, browser and gateway dependencies. Use an
   owner-only state directory and Windows ACL; never store raw tokens, lease
   values, cookies, prompts or input media in the journal.
2. Establish that the selected gateway/renderer and the planned automation
   are authorized, compatible with the actual Muse service and its terms,
   and use the account's genuine readiness/quota. Keep the upstream source
   pinned. Do not enable account fusion, tunnels, remote execution, or parallel
   render lanes. Do not install or run the unmodified reference as production.
3. Harden the actual Task API: atomic tenant-scoped key reservation before
   any await, exact key/request-hash-to-task lookup, durable account/thread
   mapping, and resume of the same verified render. An HTTP failure, restart
   failure flag, cancel flag, or matching prompt substring is not proof that
   no generation remains. Protect upstream media until CAM ACK.
4. Bind to the existing authorized CAM runner. Reuse its full-response HTTP
   helpers, /workers/config, /commands/wait?limit=20&waitSeconds=20, current
   command/job claim bodies, both independent owned leases, genuine heartbeat
   and Outbox V2, latest Original PNG verification, C1717 hero selection, and
   exact story/QA/receipt contracts. No new API keys are generated by this pilot.
   A shadow discovery poll must not impersonate the active Muse-01 runner or
   fabricate its telemetry.
5. The trusted assert_ready callback must return True only after the real CAM
   and renderer checks; a changed SHA or stale lease stops an unstarted submit.
   Construct RenderIdentity and RenderIntent from the actual claim. The
   generation revision is CAM-authorized, never increased to get around a
   refusal, timeout, attempt limit, or cooldown. GatewayAdapter accepts only
   the compatibility-tested model and an injected bounded authenticated
   transport pinned to the authorized endpoint. The exact checked hero bytes
   become the sole image reference. The prompt is the live story contract.
6. After saving the intent, submit once. On missing response preserve unknown;
   use independently verified task mapping and status, not a second POST.
   The reconcile callback runs before discovering another command. A terminal
   result must be independently confirmed before the local lane closes.
   A lost CAM ACK uses existing receipt readback/replay, not another render.
7. Download media through a task-bound, authorized downloader with URL
   allowlisting, bounded size/time, and no arbitrary redirects. Pass bytes
   to MediaSpool. Technical checks do not establish visual QA. Use actual
   print/garment/motion/character checks in the existing runner. Verify the
   CAM receipt (listing, SHA, ratio, file hash and ownership) before calling
   confirm_receipt and cleanup_verified. If artwork changes during an active
   lease, honor CAM's pinned-revision handling and never count its receipt as
   output for a new revision.
8. Cut over only after exclusive ownership of the existing worker's work has
   been confirmed and all outstanding claims/tasks reconciled. Do not start a
   second scheduler or impersonate a standby account. Live dispatcher
   construction requires verified compatibility and exclusive authorized
   ownership plus a real reconciliation callback; the library provides no
   live CLI or automatic renderer installation.

## Canary and rollout

Start with mock/read-only compatibility. Then 3 eligible new vertical videos
for the current SHA (no verified video already present), one renderer lane.
Verify genuine CAM receipt and actual QA per clip. Measure queue-to-claim,
ACK-to-next, render P50/P95, success/QA rates, ambiguous task reconciliation,
duplicate renders, actual provider limits and resource use. The 2–5 second
ACK-to-next target applies only when eligible work is available and no
cooldown or unresolved task exists. It is not a measured provider speedup.

After passing the canary, benchmark 20–30 comparable jobs against the
existing runner. Only then consider a feature-flagged production rollout.
Rollback after reconciling every active task/lease, never by clearing the
journal or blindly switching renderer. The existing production scheduler
and policies remain unchanged during this pilot.

## Open compatibility items

No live renderer compatibility, provider authorization, persistent Chrome
session, exact upstream resume or browser recovery has yet been verified.
The actual task API server needs the hardening described above. The current
source environment passes offline tests; Windows runtime/ACL/lock behavior
and the live account-specific execution callbacks still require verification.
No production video, provider task, or Drive receipt is claimed by this pilot.

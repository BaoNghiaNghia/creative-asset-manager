# CAM VPS storage / Browser QA retention

## Observed disk baseline (2026-10-19)
- `/dev/vda1`: 50 GiB class, 38 GiB used, ~9 GiB available (81% usage).
- This source workspace: ~2.4 GiB, including worktrees (~662 MiB).
- Docker Elasticsearch: image ~1.96 GB, persistent volume ~3.78 GB, container writable layer ~29 MB. The volume is **live search data**; never prune it as a cache.
- systemd journal: ~330 MB.
- Local browser QA directories had ~163 MiB in the main worktree and ~23 MiB in the Branding DNA worktree. Completed timestamp-named QA run folders were purged; the main worktree QA folder dropped to ~126 MiB and the Branding DNA QA folder to ~12 KiB. The remaining ~114 MiB `baseline-proposals` are **governed review artifacts**, not automatic temporary run captures.

These figures are partial and not a full partition inventory. In particular, native
release trees, DB storage, upload staging, temp dirs, root cache and other
un-granted paths have not been completely measured.

## New automatic cleanup behavior

`scripts/cam-ui-profile-matrix.sh` now runs QA, consumes screenshot/report data
in the profile summary, then purges only *completed timestamp-named* folders
containing `report.json` under `apps/client/.ui-qa` in its EXIT trap.
It also deletes the transient loopback preview log. This runs on success,
failure and interruption for local/VPS executions, preserving the matrix summary and its console verdict.
GitHub Actions is an exception: its ephemeral runner retains per-run captures until
post-matrix visual-review packets and the 7-day artifact upload have consumed them.
The hosted CI workspace is then discarded; QA captures are not retained on the VPS.

Set `CAM_UI_QA_PRESERVE_RUNS=1` only when a developer intentionally needs to
inspect per-run captures. The safeguard never touches `baseline-proposals`,
approved visual baselines, `production-smoke`, or unrelated user data.
For existing runs, execute:

```bash
node apps/client/scripts/ui-qa-purge-runs.mjs apps/client/.ui-qa
```

## Storage policy and next verification

- Product images and generated video intended as durable assets must be
  uploaded to Google Drive and recorded with a remote file identifier **before**
  a generation job is considered completed. At least RRUGC generation handler
  checks `stored.remote_file_id` before setting status to completed.
  This does not prove every pipeline/storage adapter follows the policy.
- Temporary downloaded/generated bytes may pass through RAM or staging disks
  while a job is executing. They must have bounded lifetime and be removed
  after successful remote confirmation; failed jobs need a controlled TTL and
  crash-safe cleanup.
- Search index volumes, PostgreSQL, logs, release environments, model caches,
  and Browser QA captures are different storage classes; not all persistent
  disk usage is media and blindly deleting directories is unsafe.
- `scripts/cam-storage-audit.sh` is a read-only inventory helper. Run it from
  a sufficiently authorized VPS shell. Review its output, identify the actual
  growing paths, confirm remote asset ID/backups and active processes, and only
  then schedule explicit, targeted deletion.

## Dispatch policy note

A connected Branding DNA Windows agent does *not* currently imply active jobs.
The backend response is hardcoded to `scan_enabled=false` and
`scan_task_dispatch_not_deployed`. Real work delivery needs an explicit,
audited dispatcher, worker lease API, and per-platform/source permission
verification before being enabled. It must not be switched on by changing a
front-end status label or forging approval flags.
